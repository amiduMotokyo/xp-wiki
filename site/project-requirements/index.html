    XP Wiki 交互化平台项目需求文档

    文档状态：初稿
    编写日期：2026-07-20
    当前阶段：需求分析与产品规划
    适用范围：XP Wiki、在线车卡、共创后台及后续战斗模拟能力

    1. 项目概述

    1.1 项目背景

    XP Wiki 当前以 MkDocs 和 Markdown 为核心，是一个用于查阅世界观、规则、职业、社群、魔法、装备等内容的静态知识库。

    随着世界观和规则体系不断扩大，新玩家需要在车卡指南、规则章节、游戏数据页面以及 Excel 角色卡之间反复查阅和填写。整个过程耗时较长，容易漏掉步骤、前置条件、附赠收益或主持人规定。

    与此同时，共创成员目前需要掌握 Git、GitHub Desktop、Markdown、VS Code、Python、MkDocs 以及导航文件格式，并自行处理拉取、提交、推送和潜在冲突。这些技术要求与创作者的核心工作无关，已经形成明显的参与门槛。

    因此，项目计划从静态 Wiki 扩展为一个面向玩家、主持人和共创成员的交互式平台。

    1.2 当前内容规模

    截至本需求文档编写时，仓库大致包含：

    • 602 篇 Markdown 文档，约 5.36 万行。
    • 420 篇正式规则与游戏数据文档。
    • 38 篇世界观与战役设定文档。
    • 141 篇共创缓冲区文档。
    • 一份包含 13 个工作表、约 408 个公式的 Excel 角色卡模板。
    • 大量职业、社群、魔法、技能、装备、状态和世界观内容之间的交叉引用。

    当前规则中还存在大量“可选”“未实装”“由主持人酌情决定”“与主持人商议”等裁量性内容。因此，新系统不能假设所有规则均可自动执行。

    2. 产品愿景

    将 XP Wiki 建设为一个以统一规则数据为基础的平台，使不同用户可以在同一套规则版本上完成以下工作：

    • 玩家无需反复翻阅规则书即可完成角色创建和成长。
    • 主持人可以配置战役规则、审核角色卡并处理例外情况。
    • 共创成员无需了解 Git 或 Markdown 即可创作和提交内容。
    • 审核成员可以查看差异、提出修改意见并控制发布。
    • 网站、角色卡、未来战斗模拟器共同使用同一份规则数据。
    • 所有正式规则、角色卡和战斗记录均可追溯到明确的版本。

    3. 产品原则

    3.1 单一事实来源

    正式规则数据应以平台数据库为唯一事实来源。公开 Wiki、车卡器、导出文件和战斗模拟器均从同一份已发布规则数据生成。

    Git 仓库可以继续作为开发、备份和导出渠道，但不再作为普通共创成员的操作入口。

    3.2 硬规则自动化，软规则集中审核

    系统应区分：

    • 硬规则：可以确定计算的条件、消耗、收益、阈值和公式，由系统自动处理。
    • 软规则：涉及人物设定、主持人裁量、数值平衡或特殊剧情的内容，由系统辅助说明并交给主持人确认。

    系统不应为了追求全自动而强行解释所有自然语言规则。

    3.3 所有计算均可解释

    任何由系统得出的数值，都应允许用户查看计算来源，例如：

    • 基础属性。
    • 种族修正。
    • 职业熟练技能加成。
    • 社群加值。
    • 装备加成。
    • 经历点附赠收益。
    • 主持人手动修正。

    3.4 版本不可静默覆盖

    已发布规则版本和已批准角色卡版本应保持不可变。规则更新后，系统可以提示迁移，但不得在用户不知情的情况下重算旧角色卡。

    4. 用户角色

    4.1 游客

    • 浏览公开世界观和规则。
    • 搜索和筛选公开内容。
    • 查看规则版本与更新记录。

    4.2 玩家

    • 创建和管理角色。
    • 通过战役邀请进入车卡流程。
    • 保存草稿并查看系统校验结果。
    • 提交角色卡给主持人审核。
    • 根据审核意见修改角色卡。
    • 导出已批准角色卡。
    • 在未来使用角色参加在线战斗。

    4.3 主持人

    • 创建战役和开团配置。
    • 设置初始经历点、时代、地区、可选种族和扩展规则。
    • 设置社群、职业、装备与购物限制。
    • 邀请玩家加入战役。
    • 审核角色卡并进行字段级批注。
    • 对软规则、特殊能力和例外情况进行批准或驳回。
    • 查看角色卡规则来源及计算过程。
    • 在未来创建战斗、控制敌人并进行手动裁定。

    4.4 共创成员

    • 使用结构化模板创建世界观或规则内容。
    • 保存个人草稿。
    • 引用已有职业、状态、魔法等实体。
    • 进行提交前自检。
    • 将一个或多个相关内容组成变更包并提交审核。
    • 根据审核意见继续修改。

    4.5 审核成员

    • 查看待审核内容及其渲染预览。
    • 查看字段级和文本级差异。
    • 检查引用、必要条件和数据完整性。
    • 添加审核意见。
    • 批准、退回或转交审核。
    • 查看变更影响范围。

    4.6 发布管理员

    • 管理用户组与权限。
    • 管理审核流程。
    • 将审核通过的变更纳入规则版本。
    • 定时或立即发布规则版本。
    • 回滚错误发布。
    • 管理旧网址重定向和数据备份。

    5. 总体业务架构

    平台由以下业务模块构成：

    1. 公开百科与检索。
    2. 规则内容管理系统。
    3. 规则版本与发布系统。
    4. 玩家角色管理系统。
    5. 引导式车卡系统。
    6. 主持人战役与审卡系统。
    7. 文件导入导出系统。
    8. 后续规则引擎与战斗模拟系统。

    各模块共同使用统一的规则实体和规则版本。

    6. 引导式车卡需求

    6.1 战役入口

    车卡流程应优先从主持人的战役邀请开始，而非从完全空白的角色卡开始。

    战役配置至少包括：

    • 战役名称与简介。
    • 故事时间和主要地区。
    • 使用的规则版本。
    • 开团经历点和预计结团经历点。
    • 是否为白卡开团。
    • 可选和禁用种族。
    • 可选社群及集群等级范围。
    • 开放的职业阶级。
    • 是否允许规则型个人天命。
    • 是否启用随从、重量、骑乘等扩展规则。
    • 初始资金倍率和购物清单。
    • 其他主持人补充说明。

    6.2 玩家车卡步骤

    系统应根据战役配置和玩家选择动态生成步骤。基础流程为：

    1. 属性骰点与属性分配。
    2. 基础信息、种族、出生地区、信仰与母语。
    3. 角色简介与天命。
    4. 角色专属技能草案。
    5. 主修魔法流派选择，可允许新玩家暂缓。
    6. 初始武器与防具。
    7. 初始基础主职和免费副职。
    8. 经历点记录与分配。
    9. 进阶职业与社群选择。
    10. 属性成长与技能经验分配。
    11. 购物、装备升级和可选随从。
    12. 完整性检查与提交审核。

    系统应根据白卡、经历点数量、种族特性和战役限制跳过不适用的步骤。

    6.3 交互要求

    • 自动保存草稿。
    • 支持撤销和恢复。
    • 显示整体进度和当前步骤。
    • 只显示当前规则下可用的选项。
    • 对不可选项目显示明确原因。
    • 实时显示经历点、资金、副职点和成长机会等余额。
    • 自动带出种族特性、职业收益、技能和装备数据。
    • 对潜在冲突提供警告，但不随意阻止主持人许可的例外。
    • 每项规则提供原文入口。
    • 每个计算结果提供计算明细。
    • 明确区分“系统已验证”和“需要主持人确认”。

    6.4 新手与熟练玩家模式

    • 新手模式：逐步解释概念、推荐常见选项、隐藏暂时无关的信息。
    • 快速模式：允许熟练玩家在总览页面批量编辑和跳转步骤。

    6.5 角色卡审核

    角色卡状态包括：

    • 草稿。
    • 待审核。
    • 审核中。
    • 需要修改。
    • 已批准。
    • 已归档。

    主持人应能够：

    • 对具体字段或能力添加批注。
    • 查看玩家修改前后的差异。
    • 对专属技能和天命分别批准。
    • 添加主持人专用的附加设定。
    • 对例外情况添加批准理由。
    • 将角色卡退回修改或整体批准。

    6.6 角色卡导出

    首期至少应支持：

    • 适合打印和分享的 PDF。
    • 可继续使用的 Excel 兼容文件。
    • 用于系统备份和迁移的 JSON。

    7. 战役与角色成长需求

    7.1 角色版本

    一个角色可以拥有多个不可变版本，例如：

    • 不同经历点阶段。
    • 不同故事年份。
    • 不同战役入口状态。
    • 不同规则版本下的迁移结果。

    新版本应记录它从哪个旧版本派生，以及发生了哪些变化。

    7.2 经历点账本

    经历点不得仅保存当前余额，应使用收支账本记录：

    • 获得或使用时间。
    • 所属战役。
    • 原因。
    • 收支数值。
    • 兑换项目。
    • 主持人批准信息。

    7.3 成长与履历对应

    经历点兑换的职业、技能、属性、语言和专属技能成长应允许关联到角色履历，帮助主持人检查 RP 合理性。

    8. 共创内容管理需求

    8.1 内容类型

    系统首期应支持以下主要内容类型：

    • 通用世界观文章。
    • 文明、地区和组织。
    • 人物与大事年表。
    • 战役简介。
    • 种族。
    • 社群。
    • 职业。
    • 魔法及魔法流派。
    • 泛用技能、武器技能和特殊技艺。
    • 战技与特殊战技。
    • 武器、防具、道具和坐骑。
    • 状态、印记和地形。
    • 单位与召唤物。
    • 规则术语和规则章节。

    8.2 结构化模板

    不同内容类型应提供对应编辑表单。例如职业模板至少包括：

    • 名称与稳定 ID。
    • 所属社群。
    • 职业阶级与主职/副职类型。
    • 概述。
    • 必要条件。
    • 关键属性。
    • 熟练技能。
    • 职业特性。
    • 各职业等级的升级收益。
    • 奖励能力及其规则数据。
    • 标签、作者和内容状态。

    叙事内容可以使用富文本和可组合内容块；机械数据必须优先使用结构化字段。

    8.3 引用选择器

    共创成员引用其他内容时，应通过搜索选择器选择稳定实体，不再手写文件路径或锚点。

    引用对象改名或调整网址时，不应导致引用失效。

    8.4 内容工作流

    基础工作流为：

    草稿 → 作者自检 → 提交审核 → 世界观/规则审核 → 退回修改或批准 → 纳入发布 → 正式上线

    工作流需要支持：

    • 多级审核。
    • 审核意见与回复。
    • 审核历史。
    • 内容锁定或并发修改提示。
    • 定时发布。
    • 撤回提交。
    • 驳回后继续编辑。
    • 发布后回滚。

    8.5 变更包

    一个创作项目可能同时包含社群简介、多个职业、专属魔法和世界观补充。系统应允许将这些内容组成一个变更包：

    • 统一提交。
    • 统一审核。
    • 显示内部依赖。
    • 原子化发布，避免只发布其中一部分。

    8.6 变更影响分析

    规则发布前应尽可能展示：

    • 哪些内容引用了本次修改的实体。
    • 哪些角色卡使用了相关规则。
    • 哪些战役固定使用旧版本。
    • 是否存在循环引用或无效引用。
    • 是否改变了必要条件、消耗、收益或数值公式。

    9. 规则数据模型

    9.1 稳定实体 ID

    每个规则实体应拥有不依赖文件路径和显示名称的稳定 ID，例如：

    occupation.basic.warrior
status.normal.bleeding
magic.elemental.fire.fireball

    显示名称、页面网址和目录结构改变时，稳定 ID 保持不变。

    9.2 规则组成

    常见机械规则优先拆分为以下结构：

    • prerequisites：必要条件。
    • costs：资源消耗。
    • grants：获得能力或内容。
    • modifiers：数值修正。
    • choice_slots：需要玩家做出的选择。
    • triggers：触发时机。
    • limits：次数和范围限制。
    • references：引用的其他规则实体。
    • manual_review_required：是否必须人工审核。
    • description：供人阅读的规则说明。

    9.3 数据结构边界

    系统不应在首期尝试把所有自然语言规则转换成可执行规则。

    优先覆盖高频且确定的 70% 至 80% 规则；复杂专属技能和特殊例外可保留自然语言，并标记为需要主持人裁定。

    10. 版本与发布需求

    10.1 内容修订

    每次保存产生可追溯修订，记录作者、时间和修改内容，可对单篇内容进行恢复。

    10.2 规则版本

    一次正式发布产生不可变的规则版本，至少记录：

    • 版本号。
    • 发布时间与生效时间。
    • 包含的变更包。
    • 更新说明。
    • 规则数据快照。
    • 发布人。

    10.3 角色卡绑定规则版本

    角色卡的每个已批准版本必须绑定明确的规则版本。规则更新后，用户可以：

    • 继续使用原版本。
    • 查看迁移影响。
    • 复制并创建新角色卡版本。
    • 在主持人批准后完成迁移。

    11. 规则引擎长期需求

    11.1 定位

    规则引擎应是与 Web 页面和游戏引擎无关的确定性核心，为车卡器、战斗模拟、批量测试和未来游戏客户端提供服务。

    规则引擎输入包括：

    • 当前游戏状态。
    • 行动者与目标。
    • 玩家选择的行动。
    • 使用的规则版本。
    • 可复现的随机种子。

    规则引擎输出包括：

    • 行动是否合法。
    • 资源消耗。
    • 结构化结算事件。
    • 新游戏状态。
    • 面向用户的规则解释。

    11.2 基础规则积木

    长期逐步支持：

    • 触发时机。
    • 目标选择。
    • 条件判断。
    • 资源消耗。
    • 普通和对抗检定。
    • 数值修正。
    • 伤害与治疗。
    • 状态、印记和地形。
    • 位移与范围。
    • 召唤与单位。
    • 持续时间。
    • 次数限制。
    • 事件响应和子弹时间。

    复杂规则应允许回退到“主持人手动结算”，避免阻塞整个系统。

    11.3 安全要求

    共创成员只能使用系统提供的白名单规则积木，不得上传或执行任意 Python、JavaScript、GDScript 或其他程序代码。

    12. 战斗模拟器长期需求

    12.1 实施策略

    战斗模拟器首版应作为网站中的“战斗实验室”，重点验证规则结算，不追求电子游戏级表现。

    首版能力包括：

    • 从已批准角色卡导入玩家单位。
    • 创建敌人和其他单位。
    • 放置格子地图和地形。
    • 展示移动、进攻和施法范围。
    • 列出合法行动。
    • 结算行动点、HP、SP、装备和状态。
    • 记录可回放的战斗事件。
    • 支持主持人暂停、改判和回滚。
    • 导出战报，用于规则复盘和平衡分析。

    12.2 游戏引擎客户端

    当出现复杂地图编辑、丰富动画、音效、离线运行或独立发行需求时，可以开发 Godot 或其他游戏引擎客户端。

    游戏引擎客户端原则上只负责：

    • 地图和动画表现。
    • 接收玩家输入。
    • 向权威规则服务提交行动。
    • 播放规则服务返回的结算事件。

    正式规则结算不应直接耦合到游戏引擎场景和动画代码。

    12.3 批量模拟

    系统应允许在不启动图形界面的情况下运行大量战斗，用于：

    • 比较职业和流派强度。
    • 评估装备与技能组合。
    • 检查极端数值。
    • 复现玩家上报的问题。
    • 为审核成员提供平衡性参考。

    13. 技术架构建议

    当前推荐采用单体优先的技术架构：

    • Django：业务系统和权限基础。
    • Wagtail：内容编辑、修订、预览和审核后台。
    • PostgreSQL：规则、角色卡、战役和版本数据。
    • 服务端渲染配合 HTMX 或少量前端组件：首期交互界面。
    • 对象存储：图片、文档、角色卡导出文件。
    • Python 规则核心：确定性计算和批量模拟。
    • 后续按需增加 WebSocket：在线多人战斗同步。

    首期不建议拆分成独立前端、独立 CMS 和独立规则微服务。待用户规模、团队规模或游戏客户端需求明确后再拆分。

    14. 非功能性需求

    14.1 可用性

    • 新玩家无需了解 Markdown、Git 或 Excel 公式。
    • 共创成员无需在本地安装开发工具。
    • 编辑表单应提供中文提示、示例和错误定位。
    • 主要操作应支持桌面浏览器，玩家车卡应尽量兼容移动端。

    14.2 数据安全

    • 重要操作保留审计日志。
    • 发布、回滚、授权和角色卡批准应记录操作人。
    • 定期进行数据库与文件备份。
    • 草稿与未公开内容只对有权限的用户可见。
    • 禁止共创成员执行任意代码。

    14.3 一致性

    • 角色卡提交和规则版本发布应使用事务保证一致性。
    • 一个变更包不得只发布部分内容。
    • 所有引用应指向稳定实体 ID。
    • 发布前运行引用、字段和规则完整性检查。

    14.4 可测试性

    • 将现有 Excel 公式与规则书范例转换为黄金测试用例。
    • 每个确定性公式应有单元测试。
    • 每个规则版本发布前应运行回归测试。
    • 随机结算应通过随机种子复现。

    14.5 性能

    • 公开 Wiki 页面应支持缓存。
    • 规则检索和选择器应支持快速搜索。
    • 车卡过程中的常见计算应即时反馈。
    • 批量模拟应在无图形界面的后台任务中执行。

    15. 首期最小可用产品

    首期目标是跑通以下完整链路：

    主持人创建白卡或低经历点战役 → 玩家完成基础车卡 → 提交 → 主持人批注和退回 → 玩家修改 → 主持人批准 → 导出角色卡

    首期纳入：

    • 用户账号和基础权限。
    • 战役配置与邀请。
    • 属性骰点和分配。
    • 基础种族。
    • 基础人设、天命和专属技能文本。
    • 五个基础职业。
    • 一级武器和防具。
    • 白卡或低经历点校验。
    • 自动保存和规则来源展示。
    • 角色卡审核。
    • Excel、PDF 或至少其中一种可靠导出格式。
    • 为上述数据提供的最小内容管理后台。
    • 内容修订和规则版本基础能力。

    首期暂不纳入：

    • 完整战斗模拟器。
    • 万能规则语言。
    • 所有进阶职业和社群的自动化。
    • 所有魔法、装备强化和扩展规则。
    • 实时多人协同编辑。
    • 电子游戏级动画和地图表现。
    • 自动判断专属技能是否平衡。

    16. 分阶段路线

    阶段一：规则地基

    • 确定内容类型、稳定 ID 和版本规范。
    • 建立最小内容后台。
    • 导入基础种族、基础职业和初始装备。
    • 将关键 Excel 公式转为测试和服务端计算。
    • 建立审核与发布基础流程。

    阶段二：车卡闭环

    • 实现战役配置与邀请。
    • 实现新手引导式车卡。
    • 实现主持人审卡。
    • 实现角色卡版本与导出。
    • 用真实新玩家进行可用性测试。

    阶段三：完整成长体系

    • 经历点账本与履历。
    • 属性和技能成长。
    • 社群与进阶职业。
    • 魔法、购物和装备强化。
    • 旧角色卡版本迁移。

    阶段四：全面共创迁移

    • 扩充所有内容模板。
    • 实现变更包和影响分析。
    • 迁移现有正式文档。
    • 自动生成公开百科页面和导航。
    • 为旧网址建立重定向。

    阶段五：规则引擎与战斗实验室

    • 建立确定性战斗状态和事件模型。
    • 实现基础移动、检定、进攻、防守和伤害。
    • 实现状态、印记、地形与回放。
    • 实现主持人手动裁定和回滚。
    • 建立无图形批量模拟能力。

    阶段六：可选游戏客户端

    • 根据用户反馈决定是否开发 Godot 或其他游戏引擎客户端。
    • 复用既有规则版本、角色卡和战斗事件协议。
    • 增强地图、动画、音效和离线体验。

    17. 首期验收指标

    17.1 玩家体验

    • 新玩家能够在不直接编辑 Excel 的情况下完成基础角色卡。
    • 所有必填步骤都有明确状态，不会无提示遗漏。
    • 不可选职业、种族或装备能显示具体原因。
    • 玩家能查看关键计算的来源。
    • 角色卡可保存、恢复、提交和导出。

    17.2 主持人体验

    • 主持人能创建可复用的战役配置。
    • 主持人能在一个界面内看到角色卡错误和待确认项。
    • 主持人能对具体字段提出修改意见。
    • 审核通过后生成不可变的角色卡版本。

    17.3 共创体验

    • 共创成员无需使用 Git、Markdown 或本地开发工具即可创建首期内容类型。
    • 内容可以保存草稿、预览、提交和退回修改。
    • 审核人可以查看修改差异和引用关系。
    • 未经批准的内容不会出现在正式规则中。

    17.4 数据一致性

    • 车卡器和公开规则页读取同一份已发布数据。
    • 已批准角色卡明确绑定规则版本。
    • 规则发布不会静默修改旧角色卡。
    • 发布前能够发现无效实体引用。

    18. 主要风险

    18.1 过早追求万能规则引擎

    规则体系包含大量特殊情况。如果首期要求所有规则都可执行，容易导致开发周期失控。应优先覆盖高频确定性规则，并保留人工裁定出口。

    18.2 Markdown 与数据库长期双轨

    如果两边都允许修改，会迅速产生内容冲突。迁移期应明确主数据来源，并尽量采用单向导入或单向导出。

    18.3 规则发布破坏旧角色卡

    如果没有版本快照，任何平衡调整都可能改变历史角色。规则版本和角色卡版本必须从早期开始建设。

    18.4 内容模型设计过度或不足

    模型过于自由会退化成另一套 Markdown；模型过于严格则无法容纳特殊创作。应通过若干典型社群、职业、魔法和复杂技能反复验证模型。

    18.5 游戏表现抢占规则开发资源

    地图动画能快速产生可见成果，但最核心的风险仍然是规则一致性。战斗实验室应先验证规则结算，再投入游戏客户端表现。

    19. 待确认事项

    以下内容需要在正式设计和开发前继续确认：

    • 首期主要面向白卡，还是指定一个经历点区间。
    • 第一批纳入的基础种族范围。
    • 是否继续将 Excel 作为官方导出格式。
    • 战役配置中哪些规则必须由主持人控制。
    • 世界观审核与数值审核是否由不同用户组负责。
    • 规则版本号与发布时间的管理规范。
    • 旧 Markdown 在迁移期是否继续公开发布。
    • 部署地区、域名、账号登录方式和服务器预算。
    • 移动端车卡的优先级。
    • 战斗实验室预期支持的地图规模和同时在线人数。
